## 1. 一句话说清楚我们做了什么

> 我们让一辆**麦克纳姆轮小车**，在 **3.6m × 3.6m** 的比赛场地里，**自己认路**走到 6 个任务点，用**摄像头 + 大模型**看到物体，用**机械臂**抓起来放到指定位置，全程**不碰围栏、不超时**。

**关键技术挑战**：
- 碰围栏 → 直接判负 → 运动控制必须绝对安全
- 30 秒不动 → 直接判负 → 必须 fail-fast，卡了就放弃继续走
- 麦克纳姆轮会漂移 → 航向必须死死锁定
- 抓取物体种类赛前才公布 → 不能用固定模板，必须用大模型视觉理解

## 3. 软件架构分层

整个系统按 **4 层** 组织，每层只管自己的事：

```
┌────────────────────────────────────────────────────────┐
│  第4层: 运动执行脚本层                                   │
│  goal_nav.py / ten_point_race.py / seven_point_test.py │
│  ten_point_odom_race.py / auto_navigation_grasp.py     │
│  功能: 读 tf 位姿 → 算路径 → 发 cmd_vel / 调用抓取     │
├────────────────────────────────────────────────────────┤
│  第3层: 导航定位层                                      │
│  amcl + map_server + gmapping                          │
│  功能: 激光 → 定位/建图 → 发布 map→odom tf              │
├────────────────────────────────────────────────────────┤
│  第2层: 传感器融合层                                    │
│  EKF (robot_localization) + Madgwick 滤波器            │
│  功能: 轮速 + IMU → 融合里程计 → 发布 odom→base tf      │
├────────────────────────────────────────────────────────┤
│  第1层: 驱动层                                          │
│  rosserial (底盘) + rplidar 驱动 + astra 相机驱动       │
│  功能: 读传感器原始数据, 写 cmd_vel 到底盘              │
└────────────────────────────────────────────────────────┘
```

### 为什么不直接用 move_base（重要！答辩高频问题）

ROS 标准导航栈 `move_base` 包含**全局规划**（A* / Dijkstra）+ **局部规划**（TEB / DWA）。

**我们不用它的原因**：
- TEB/DWA 是**反应式避障**——它看到障碍会"贴着走"，但比赛规则是**碰围栏直接判负**
- TEB 的轨迹是**光滑曲线**（斜着走），而麦轮斜着走会漂移，很难控制
- 我们只需要**沿 X 轴走 → 沿 Y 轴走 → 原地转**，三个动作就够了

**我们的方案**：自己写 A*（全局规划）算出一条安全路径，然后用**锁航向原语**执行（只发 `cmd_vel.linear.x` 和 `.y`，`angular.z` 只用于原地转），不走曲线。

## 4. 核心数据流（图 + 解释）

### 数据怎么从传感器流到电机

```
┌─────────────────────────────────────────────────────────────────────┐
│                    ▼▼▼ 数据流走向 ▼▼▼                                │
│                                                                     │
│  轮式编码器 ──→ /raw_odom ──┐                                       │
│                              ├──→ [EKF] ──→ /odom ──→ tf: odom→base │
│  MPU6050 IMU ──→ /imu/data ──┘       ↑                              │
│                                       │ 只采轮速 vx/vy + IMU yaw    │
│                                       │ 轮速的角速度 vyaw 不用      │
│  RPLidar C1 ──→ /scan ──→ [amcl] ──→ tf: map→odom                  │
│                                ↑                                    │
│                            读 comp.yaml 静态地图                    │
│                                                                     │
│  tf: map→base_footprint ← 上面两段 tf 链合成                        │
│          │                                                          │
│          ▼                                                          │
│  运动脚本读 tf 位姿 → P 控制 → /cmd_vel → 底盘 MCU → 电机          │
│                                                                     │
│  相机 ──→ /camera/rgb/image_raw ──→ [VLM server] ──→ /Pose         │
│                                                   (检测框坐标)      │
│                                                       │             │
│                                                       ▼             │
│                                              [xArm 机械臂]           │
│                                              像素→机械臂坐标转换    │
│                                              串口发 JSON 抓取       │
└─────────────────────────────────────────────────────────────────────┘
```

### 关键要点

1. **EKF 融合策略**：里程计的 `vx`、`vy`（线速度） + IMU 的 `yaw`、`vyaw`（航向角和角速度）。里程计自己的角速度**不用**——因为轮子打滑测的角速度是错的，IMU 的 yaw 更准。
2. **建图与定位互斥**：gmapping 和 amcl 都发布 `map→odom` 这一段 tf。同一时间只能起一个，否则 tf 树打架。
3. **运动脚本闭环节**：脚本读 `map→base_footprint` tf 获取当前位置 → 算误差 → P 控制器算速度 → 发 `cmd_vel` → 底盘执行 → 下一帧再读 tf。这就是闭环。

## 5. TF 坐标树（谁生谁、谁吃谁）

```
map                                          ← gmapping (建图) 或 amcl (定位) 发布
 └── odom                                    ← EKF (bringup) 发布
      └── base_footprint                     ← EKF (bringup) 发布
           ├── base_link                      ← static (固定偏移 0,0,0)
           ├── laser                          ← static (雷达安装位置)
           └── imu_link                       ← static (IMU 安装位置)
```

### 每个 frame 干什么

| Frame | 谁发布的 | 代表什么 | 注意 |
|-------|---------|---------|------|
| `map` | map_server（定位） / gmapping（建图） | 世界坐标系，固定不动 | 地图原点 = 建图起点 |
| `odom` | EKF | 里程计坐标系，开机归零 | 长时间会漂移 |
| `base_footprint` | EKF | 机器人在 odom 中的位姿 | 投影到地面，没有高度 |
| `base_link` | static_transform | 机器人本体中心 | 在 base_footprint 正上方 |
| `laser` | static_transform | 雷达安装位置 | 用来把激光数据从雷达坐标系转到机器人坐标系 |
| `imu_link` | static_transform | IMU 安装位置 | 用来把 IMU 数据转到机器人坐标系 |

### 关键性理解

**`map → base_footprint` 是怎么来的？**
- 不是单一节点发布的！ROS 的 tf 树是链式结构：
  - `map → odom`（amcl 发布）
  - `odom → base_footprint`（EKF 发布）
  - 查询 `map → base_footprint` = ROS 自动把两段 tf 链**拼接**起来

这就是为什么**即使 amcl 挂了，纯里程计脚本还能用 `odom → base` 继续跑**——它只查后半段。

## 6. 导航流水线（全流程拆解）

### 比赛全流程时序

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ 开机清场  │ →  │  建图    │ →  │  定位    │ →  │ 跑脚本   │
│ 摆好起点  │    │ 存地图   │    │ 加载地图 │    │ 抓放执行 │
└──────────┘    └──────────┘    └──────────┘    └──────────┘
```

#### 阶段 1：建图（赛前做好，比赛只用一次）

```bash
roslaunch abot bringup.launch      # 起底盘 + IMU + EKF
roslaunch abot lidar_slam.launch   # 起雷达 + gmapping

# 手动遥控小车走遍场地每个角落
# gmapping 根据激光 + 里程计实时拼图

rosrun map_server map_saver -f ~/catkin_ws/src/abot_project/abot/maps/comp
# 存成 comp.pgm (图片) + comp.yaml (配置文件)
```

**建图原理**（Gmapping）：
- 粒子滤波 SLAM（一种用很多"猜测"来估计位置和地图的算法）
- 每个粒子 = 一个可能的机器人位置 + 一张地图
- 激光匹配得分高的粒子保留，得分低的淘汰
- 粒子数量 50 个（`particles=50`）

**建图关键**：
- 车必须从**比赛起点**开始建图，车头朝 +X
- 这样地图原点 = (0,0) = 比赛起点，后面 amcl 的初值就是 (0,0,0)，完美对齐
- 建图慢一点、稳一点，别急转弯

#### 阶段 2：定位（比赛时）

```bash
roslaunch abot bringup.launch      # 底盘 + IMU + EKF
roslaunch abot localize.launch     # 雷达 + map_server(comp.yaml) + amcl
```

**amcl 定位原理**（Adaptive Monte Carlo Localization）：
- 自适应蒙特卡洛定位（amcl 是 gmapping 的"只用定位不建图"版本）
- 也是粒子滤波，但不更新地图，只估计机器人在地图上的位置
- 激光扫描跟地图比对 → 给每个粒子打分 → 权重高的粒子留下 → 机器人位置=粒子群中心
- 粒子数 800~3000，自适应调整（收敛后减少，发散时增加）

#### 阶段 3：导航执行（运动脚本的工作）

```
           ┌─ 读 tf 获取当前位置
           │
           ├─ 算目标位置和当前位置的误差
           │
           ├─ L 形分解（先 X 后 Y 或先 Y 后 X）
           │
           ├─ P 控制器算速度
           │
           ├─ 发 cmd_vel
           │
           └─ 回到第一步（20Hz 循环）直到到达
```

**L 形分解**：
- 不斜着走！路线永远是 "先沿 X 轴走到目标 X → 再沿 Y 轴走到目标 Y"
- 或者反过来，取决于哪个方向误差更大
- 全程锁定出发时的航向角

为什么要这样设计？如果不锁航向，麦轮的漂移会让车偏转，偏转后激光跟地图对不上，amcl 定位就丢了。

**P 控制器**：
```
速度 = K × (目标位置 - 当前位置)
```

简单到不能再简单——位置差越大跑越快，越靠近越慢，到了就停。

- `V_LIN = 0.20`：最快 0.2 m/s（约每秒 20 cm）
- `K_LIN = 4.0`：强比例控制
- `K_LIN_HOLD = 5.0`：非主运动轴用更强增益（压住漂移）

### 目标航向（goal_nav.py 独有）

**goal_nav.py** 是唯一带**全局规划器**的脚本：
1. 收到 rviz 的 2D Nav Goal
2. 读取 `/map` 栅格地图
3. 膨胀障碍物（默认 0.2m 半径，留安全余量）
4. **A* 算法** 搜路径（4 连通，只走上下左右，不走对角线）
5. 路径简化：只保留方向改变的拐点
6. 沿拐点 L 形执行

**A* 搜索**：
```
代价 = 已走步数 + 曼哈顿距离到终点

启发函数（曼哈顿距离）：
  h = |x当前 - x终点| + |y当前 - y终点|
  
A* 保证：在 4 连通栅格上，找到的路径是步数最短的
```

### 导航流程总结对比

| 模式 | 位姿源 | 有无全局规划 | 适合场景 |
|------|-------|------------|---------|
| 手动导航（goal_nav.py） | amcl (map) | ✅ A* | 调试、临时去某个点 |
| 比赛脚本（ten_point_race.py） | amcl (map) | ❌ 硬编码坐标 | 正式比赛 |
| 保底脚本（ten_point_odom_race.py） | EKF (odom) | ❌ 硬编码坐标 | amcl 挂了时兜底 |

### 7.1 VLM 视觉检测（server.py）

**做什么**：相机拍照 → 发给大模型 → 模型告诉你物体在图片的哪个位置（像素坐标）

启动：
```bash
roslaunch vl_locate vl_locate.launch
# 内部起：
#   - astra camera 驱动（相机节点）
#   - image_zoomer（图像缩放，降低分辨率提高处理速度）
#   - vlm_detection_node（VLM 检测服务，Python3）
```

**工作流程**：
1. 运动脚本到达抓取点 → `rospy.set_param('/grab', True)` 告诉机械臂准备抓取
2. 运动脚本调用 `/vlm_detection` 服务，传入物体名称（如"蓝色方块"）
3. VLM server 从 `/new_topic` 取最新一帧图像 → 存到本地
4. 构建提示词：*"检测图中的蓝色方块"* → 编码图片为 base64 → 发 API
5. 通义千问 VL-Max 返回 JSON：`{"label": "蓝色方块", "bbox_2d": [x1,y1,x2,y2]}`
6. 提取中心坐标 `( (x1+x2)/2, (y1+y2)/2 )` → 发布到 `/Pose` 话题
7. `DetectionArray` 消息带着坐标 → 机械臂节点收到

**网络依赖**：VLM 需要联网调用通义千问 API。所以比赛现场必须有 WiFi。

**为什么用大模型而不用传统视觉**：
- 比赛物体**赛前才公布**，没法提前训练
- 大模型零样本就能理解"蓝色方块"、"红色圆柱"这种描述
- 传统 CV 需要提前知道颜色、形状、特征点，太死板

### 7.2 机械臂控制（gg.py + xarm_driver.py）

**做什么**：收到像素坐标 → 转成机械臂坐标 → 控制 6 个舵机去抓

启动：
```bash
roslaunch ZachLab_grasp grasp.launch
```

**坐标转换**（像素 → 机械臂）：
```
相机和机械臂的坐标系不同，做了一个"两点标定"：

在桌面上放两个已知点：
  点 A: 像素坐标 (66, 361) ↔ 机械臂坐标 (-60, 125)
  点 B: 像素坐标 (584, 125) ↔ 机械臂坐标 (135, 195)

用 numpy.interp() 做线性插值：
  任意像素 X → 机械臂 X = np.interp(x, [66, 584], [-60, 135])
  任意像素 Y → 机械臂 Y = np.interp(y, [125, 361], [195, 125])
```

**机械臂通信协议**（xArm JSON）：
```json
// 控制位姿
{"RikibotxArmCmd": 1, "Pose": {"x": 100, "y": 50, "z": -110, "rotary": 90}, "time": 1000}

// 控制夹爪
{"RikibotxArmCmd": 2, "Gripper": 700, "time": 1000}

// 参数含义:
//   x,y,z: 末端位置（mm）
//   rotary: 末端旋转角度（°）
//   Gripper: 700=闭合, 150=打开, 500=默认
//   time: 运动时长（ms）
```

**抓取流程（gg.py）**：
```
① 打开夹爪 → ② 计算抓取位姿 → ③ 移动到物体上方 → ④ 夹爪闭合 → ⑤ 抬起到安全高度
```

**放置流程（gg.py）**：
```
① 计算放置位姿 → ② 移动到放置位 → ③ 夹爪打开 → ④ 回到初始位
```

**两种模式**：
- `continuous_mode = True`：持续监听 `/Pose`，有新物体就抓
- `continuous_mode = False`：抓一次就停（目前用 True）

### 7.3 运动脚本 ↔ 抓取的握手协议

运动脚本和机械臂通过两个 ROS 参数通信：

```
         ten_point_race.py                      gg.py
               │                                  │
 ① 到达抓取点  │                                  │
 ② rospy.set_param('/grab', True) ─────────→   ③ 读到 /grab=True
               │                                 ④ 调用 VLM 检测
               │                                 ⑤ 执行抓取
 ⑥ 等待 25s ←───────────────────────            ⑦ 抓完 /grab=False
                                              ⑧ rospy.set_param('success', True)
```

这 25 秒等待（`GRASP_WAIT_SEC = 25`）是给 VLM 调用 + 机械臂运动的时间。实际可以通过检测 `success` 参数来动态等待，但目前用固定等待更简单可靠。

## 8. 比赛脚本通解

### 8.1 `ten_point_race.py` — 主战脚本

**定位**：正式比赛用

**路线**（map 系坐标）：
```
进走廊 (2.4, 0.6) → P1 抓 (3.6, 0.6) → P2 放 (2.4, 0.6)
→ 上移 (2.4, 1.8) → P3 抓 (3.6, 1.8) → P4 放 (2.4, 1.8)
→ 上移 (2.4, 2.6) → P5 抓 (3.6, 2.6) → P6 放 (2.4, 2.6)
→ 终点 (2.4, 2.0)
```

**路线为什么这样设计**：
```
场地 3.6 × 3.6 米，中间有挡板。
上排: 点1(抓)   点3(抓)   点5(抓)    ← x=3.6
下排: 点2(放)   点4(放)   点6(放)    ← x=2.4

我们的走法：永远在 x=2.4 走廊走，到目标 y 后，darting到 x=3.6 抓取，再退回 x=2.4 放置。

这样永远不会撞到中间挡板！
```

**数据类型**：`(x, y, yaw, action, object)`
- `x, y`：目标位置（map 系）
- `yaw`：目标朝向（弧度）
- `action`：`grab` / `place` / `pass`
- `object`：VLM 搜索的物体名称
- `pass`：只导航不抓放

**赛前必须改的**：把 `WAYPOINTS` 里 P1/P3/P5 的 `object` 改成裁判公布的物品

**执行方式**：
```
goto(x, y, yaw):
  第1步: drive_to_point(x, cur_y)       # 先走到目标 X（保持当前 Y）
  第2步: drive_to_point(x, y)           # 再走到目标 Y（保持 X）
  第3步: rotate_to(yaw)                 # 原地转到目标朝向

  drive_to_point 内部是 20Hz 的 P 控制循环
```

### 8.2 `ten_point_odom_race.py` — 保底脚本

**定位**：amcl 挂了/定位栈不可用时的兜底方案

**和主脚本的三大区别**：
1. **位姿源不同**：用 `odom → base_footprint` 而不是 `map → base_footprint`。这样只需起 `bringup.launch`，不需要雷达和 amcl。
2. **无抓放**：纯导航，只走点，不调用 VLM 和机械臂。所以路线只有坐标，没有 `action` 字段。
3. **必须物理摆位**：`odom` 坐标系开机归零，所以车必须**物理摆到比赛起点**再开机，否则坐标全错。

**使用场景**：
- 比赛现场定位栈出问题，临时用纯里程计保分
- 注意：纯里程计没有回环校正，走 3 米会漂移几厘米，但几个点的到达分（5 分/个）比完全放弃强

### 8.3 `seven_point_test.py` — 可达性测试

**定位**：验证 7 个比赛点都能导航到达

**和十点脚本的区别**：
- 只有导航，没有抓放
- 7 个点 = 6 个比赛点 + 终点
- 用来验证 amcl 定位是否正常、L 形分解是否可以到达每个点

### 8.4 `goal_nav.py` — 手动导航

**定位**：调试工具。rviz 上点哪儿，车就去哪儿

**独特之处**：
- 唯一带 **A* 全局规划**的脚本
- 唯一能在 **rviz 上实时发目标**的脚本
- 订阅 `/move_base_simple/goal`（和标准 ROS 导航一样的话题名，方便 rviz 集成）
- 会发布 `/goal_nav/path` 到 rviz 显示规划路径

**调试用途**：
- 验证地图是否正确
- 验证 amcl 定位是否收敛
- 临时测试某个特定点的可达性

### 8.5 `auto_navigation_grasp.py` — 旧版（历史遗留）

> **注意**：这是**旧版**脚本，依赖 `move_base` actionlib。已被 `ten_point_race.py` 取代。源码仍保留但不再维护。

**和当前方案的关系**：
- 旧方案：`move_base` 做路径规划 + 执行 → 贴挡板风险
- 新方案：自己控制 `cmd_vel` → 安全可控

它证明了"为比赛走安全路线"需要自定义运动控制，也直接导致我们决定绕过 move_base。

## 9. 核心算法原理解析

### 9.1 A* 路径搜索（goal_nav.py）

**干什么**：在栅格地图上找到从 A 到 B 的最短路径

**细节**：

```
1. 把 /map 的栅格转成二进制阻挡图
   - 占用值 ≥ 50 或 = -1（未知）→ 视为障碍
   - 障碍按 inflation_radius（默认 0.2m）向外膨胀一圈
   - 膨胀方法：对每个障碍栅格，把它半径 R 内的邻居全标记为阻挡
     R = ceil(0.20 / 0.05) = 4 个栅格

2. A* 搜索（4 连通，只走上下左右）
   
   g(n) = 从起点到当前点的步数
   h(n) = |x_n - x_goal| + |y_n - y_goal|（曼哈顿距离）
   f(n) = g(n) + h(n)
   
   每次从优先队列取 f 值最小的栅格扩展
   把邻居加入队列，更新 g 值（只保留最小的）
   找到终点 → 回溯路径

3. 路径简化
   - 原始的 A* 路径是一堆相邻栅格
   - 只保留"方向改变"的拐点
   - 例如: 右右右右 → 上上上上 → 右右右右
   - 简化后只剩 3 个点（起点、拐点、终点）
   - 这样就从"锯齿路径"变成"直线段"
```

**为什么 A* 比 Dijkstra 快？**
- Dijkstra 是"四个方向平均散开" → 像水波扩散
- A* 是"朝目标方向优先扩散" → 像聚光灯照过去
- 在比赛场地（3.6×3.6m，约 72×72 栅格）上，两者速度差别不大，但 A* 学理上更优

### 9.2 P 控制器（以误差驱动的简单控制）

**干什么**：告诉电机"差多少跑多快"

```
位置误差 e_x = 目标_x - 当前_x
位置误差 e_y = 目标_y - 当前_y

vx = clamp(K_lin * e_x, -V_lin_max, V_lin_max)
vy = clamp(K_lin * e_y, -V_lin_max, V_lin_max)

但有个技巧（K_LIN_HOLD）：
  如果 |e_x| < |e_y|：
    vx = K_LIN_HOLD * e_x    # 非主运动轴，用更大增益压漂移
    vy = K_LIN * e_y         # 主运动轴，正常增益
  否则反过来

为什么要区分主次轴？
  假设要往东走 1m，但有一点点向北的误差
  如果不压北向漂移，车会斜着走
  压住北向增益 → 车几乎直着往东走
```

**角速度控制**：
```
航向误差 e_yaw = 目标_yaw - 当前_yaw
wz = clamp(K_yaw * e_yaw, -V_rot_max, V_rot_max)

死区: |e_yaw| < 0.02 rad → 不动（防止反复微调）
最小速度: |wz| < V_ROT_MIN → 强制提到 V_ROT_MIN（克服静摩擦）
```

**P 控制 vs PID**：
- 我们只用 P（比例），没用 I（积分）和 D（微分）
- 为什么？因为 P 已经够用——我们要的是"到点停车"，不是"精确跟踪一条路径"
- D 对噪声敏感（IMU 噪声大），I 可能引起超调（容易撞墙）

### 9.3 EKF 传感器融合

**干什么**：把轮速里程计和 IMU 数据融合成一个更准的位姿估计

```
输入 1: /raw_odom（轮速）
  用: vx, vy（线速度）
  不用: yaw, vyaw（角度、角速度）→ 轮子打滑时角度是错的

输入 2: /imu/data（IMU）
  用: yaw, vyaw（航向角和角速度）→ IMU 比轮子准
  不用: x, y（位置）→ IMU 没法测位置

EKF 的作用：
  ① 用轮速算"走了多远"（vx, vy 积分 → 位置变化）
  ② 用 IMU 算"转了多大角度"（yaw, vyaw 积分 → 朝向变化）
  ③ 两个信息互补，输出一个融合后的 /odom
```

**那 EKF 不完美时呢？**
- 轮子打滑 → 里程计多报位移 → EKF 输出的 odom 有累计误差
- 所以 odom 走 3 米会漂移几厘米
- 这也就是为什么我们需要 amcl（激光定位）来校正这个漂移
- odom 准在"短时间"，map 准在"绝对位置"
- tf 链 `map → odom → base` 巧妙结合了两者

### 9.4 L 形分解 + 锁航向

**核心思想**：不斜穿，只走直线段

为什么这样规避"碰挡板判负"：
```
斜着走的问题:
  map     挡板
  ┌───────┬───────┐
  │       │ █████ │
  │ 起点  │       │
  │  ╲    │ 目标  │ ← 斜线会穿过挡板角
  │   ╲   │       │
  └───────┴───────┘

L 形分解:
  ┌───────┬───────┐
  │       │ █████ │
  │ 起点──┤       │ ← 先沿 X 到拐点
  │       │──目标 │ ← 再沿 Y 到目标
  └───────┴───────┘
  路线完全不碰挡板
```

**锁航向**：
```
出发时的角度 = θ
全程保持 θ 不变，直到原地转

① 先走 X 方向（车身朝 θ） → linear.y 为主
② 再走 Y 方向（车身仍朝 θ）→ linear.x 为主
③ 原地转 θ_yaw → 只用 angular.z
```

### 9.5 VLM（视觉大模型）检测

**不是什么新技术**，就是**把图片发给 AI，让 AI 告诉你物体在图片的哪个像素位置**。

```
① 拍照 → 存为 JPG
② 编码为 base64 字符串
③ 构建对话：
   用户: [图片] "检测图中的蓝色方块"
   模型: {"label": "蓝色方块", "bbox_2d": [120, 200, 300, 350]}
④ 解析 JSON → 计算中心 (210, 275) → 发布给机械臂
```

**为什么用通义千问 VL-Max**：
- 国产大模型，API 稳定
- 支持多模态（图片 + 文字输入）
- 支持 bbox 输出（告诉物体在图片的哪个区域）
- 量级足够大，识别准确率高

**局限性**：
- 需要网络 → 比赛现场 WiFi 必须稳定
- 耗时约 2-5 秒/次 → 就是 GRASP_WAIT_SEC 设 25 秒的原因（含机械臂运动）
- 小物体可能识别不准 → 需要合理布置任务物体

### 9.6 Gmapping SLAM（建图算法）

```
输入: /scan（激光数据）+ /odom（里程计）
输出: /map（栅格地图）

核心逻辑：
 ① 初始化：均匀散布 N=50 个粒子
 ② 运动更新：根据里程计移动每个粒子
 ③ 观测更新：用激光扫描跟粒子的地图比对 → 打分
 ④ 重采样：高分粒子复制，低分粒子淘汰
 ⑤ 更新地图：根据高分粒子的路径更新栅格占用概率
 ⑥ 重复②-⑤，每 2 秒发布一次地图
```

### 9.7 AMCL（定位算法）

```
输入: /scan（激光）+ /map（已知地图）+ /odom
输出: map → odom tf（定位结果）

和 Gmapping 的核心区别：
  Gmapping: 不知道地图 → 边建图边定位
  AMCL: 已知道地图 → 只定位不建图

AMCL 自适应体现在哪里？
  粒子数自动调整：
  收敛（粒子群很集中）→ 减少粒子数（省计算）
  发散（位置不确定）→ 增加粒子数（提高覆盖）
```

## 11. 常见故障树（按症状查根因）

### 症状 1：车启动后不动（30s 规则注意！）

```
车不动
├─ 检查 rosnode list | grep amcl
│  ├─ 没有 amcl → localize.launch 没起或起失败
│  │  └─ 检查 roscore 是否在跑
│  └─ 有 amcl → 下一步
├─ 检查 rostopic echo /scan 有数据吗？
│  ├─ 没有 → 雷达被占用（有残留进程）
│  │  └─ killall -9 roslaunch rplidarNode 然后重来
│  └─ 有 → 下一步
├─ 检查 rosrun tf tf_echo map base_footprint
│  ├─ 没输出 → amcl 没收敛（缺 /scan? 地图文件不对?）
│  │  └─ 检查 comp.yaml 路径和内容
│  └─ 有输出 → 下一步
└─ 跑脚本时检查终端日志
   ├─ "no tf pose" → tf 没查到
   ├─ "TIMEOUT" → 走太慢或卡住了
   └─ "no /map yet" → 地图没收到
```

### 症状 2：车走歪（斜着走、漂移）

```
车走歪
├─ 检查 K_YAW（角速度 P 增益）→ 太小则航向修正不够
├─ 检查 K_LIN_HOLD → 太小则压不住漂移
├─ 检查地面是否光滑 → 麦轮在光滑地面打滑严重
├─ 检查 V_LIN → 太快→漂移大→应降到 0.15 试试
└─ 检查 IMU 工作正常吗？
   ├─ rostopic echo /imu/data → 看 yaw 是否稳定变化
   └─ 异常 → 检查 imu_calib.yaml 标定参数
```

### 症状 3：到达误差大（停歪了）

```
到点停歪
├─ POS_TOL 是不是设太大了？0.04m=4cm，够用
├─ 检查 V_LIN 是不是太大 → 到点过冲
├─ 检查 V_LIN_MIN 是不是太小 → 最后几毫米走不动
└─ 检查地面 → 有坡度/缝隙会影响
```

### 症状 4：VLM 检测不到物体

```
VLM 没反应
├─ 网络通吗？→ curl 通义千问 API
├─ 相机有画面吗？→ 检查 /camera/rgb/image_raw
├─ 调用服务了吗？→ rosservice call /vlm_detection
├─ server.py 在跑吗？→ rosnode list
├─ 光线是不是太暗？→ 开灯
└─ 物体跟提示词匹配吗？→ "蓝色方块" vs 实际物体颜色
```

### 症状 5：机械臂不动

```
机械臂不动
├─ rosserial 通吗？→ /dev/ttyACM0 存在吗？
├─ 串口权限？→ ls -l /dev/ttyACM0, 需要 dialout 组
├─ gg.py 日志报什么？
│  ├─ "检测到物体" → VLM 通了，但坐标转换可能出错
│  └─ "未检测到物体" → VLM 还没返回结果
└─ 舵机通电了吗？→ 机械臂电源线插好了吗？
```

### 症状 6：建图歪了/地图重影

```
建图有问题
├─ gmapping 启动了吗？
├─ 建图时车动得太快？→ linearUpdate 改 0.1
├─ minimumScore 太小？→ 提到 150+
├─ 雷达装歪了？→ 检查 laser static tf
└─ 里程计标定了吗？→ linear_scale=1.014 是校准过的
```

### 症状 7：比赛因"碰挡板"被判负

```
碰挡板
├─ 路线离挡板太近 → 修改 WAYPOINTS 留更多余量
├─ 漂移太大碰到侧面 → 检查锁航向参数
├─ L 形分解的拐点离挡板太近 → inflation_radius 改大
└─ 执行 goal_nav.py 时 A* 膨胀半径不够
   └─ inflation_radius 默认 0.2m，可改 0.25m
```

## 12. 答辩可能问到的问题

### Q1：为什么要绕过 move_base？

> **答**：move_base 的局部规划器（TEB/DWA）是反应式避障，它会贴着障碍物边缘走。我们比赛规则规定"碰围栏直接判负"，所以任何贴障碍物走的策略都太冒险。我们的方案是：全局路径走安全车道中线，用 L 形分解 + 锁航向原语执行，严格不斜穿、不贴边。这是"安全第一"的工程选择。

> **追问：不用 move_base 不是放弃了很多 ROS 现成功能吗？**
> 
> 是的。但我们保留全局规划（A*），自己去掉了局部规划器。全局规划在静态地图上是确定性的，没有问题。运动执行我们重写了一套 P 控制器，按比赛需求定制。**工程上不应该因为"框架提供了"就用，而应该因为"我需要"才用。**

### Q2：麦克纳姆轮和普通轮子比有什么优劣？

> **答**：优势是**全向移动**——可以前后、左右、原地转，不用转弯掉头。在狭窄的比赛场地（3.6×3.6m）里，全向移动可以走更优化的路线。劣势是**效率低、容易打滑**——麦轮靠小滚轮摩擦，地面不干净或有灰时漂移明显。所以我们用了强 P 增益压漂移（K_LIN_HOLD = 5.0）和 20Hz 高频率控制循环来补偿。

### Q3：EKF 的配置为什么轮速角速度和 IMU 加速度都不采？

> **答**：
> - **轮速角速度不采**：麦克纳姆轮在转弯时半数轮子打滑，轮速算出来的角速度是错的，用了反而污染数据。
> - **IMU 加速度不采**：Jetson Nano 算力有限，IMU 加速度噪声大，处理它需要额外的计算资源，对结果提升不明显。
> - **关键原则**：传感器融合不是"越多越好"，是"越可靠越好"。只采最可靠的信源。

### Q4：A* 为什么用 4 连通而不用 8 连通？

> **答**：8 连通（允许斜走）生成的路径有斜线段，执行斜线段时车会斜着走——麦克纳姆轮斜着走漂移最大。4 连通（上下左右）生成的路径只有水平和垂直线段，对应我们的 L 形分解，全程锁航向，漂移最小。**算法的选择受制于物理约束。**

### Q5：为什么用大模型做视觉检测？传统视觉不行吗？

> **答**：比赛物体赛前才公布，我们无法预知要抓什么。传统 CV 需要预先训练或知道特征（颜色、形状、轮廓），大模型零样本就能理解"蓝色方块"这种自然语言描述。当然代价是：需要联网、有 2-5 秒延迟、依赖 API 稳定性。我们认为是值得的——**灵活性的收益大于延迟的代价。**

### Q6：你们的定位精度能达到多少？

> **答**：
> - **amcl 定位**：在良好环境下，`map → base_footprint` 精度约 **2-5 cm**
> - **纯里程计**：短期（1m 内）约 1-2 cm，走完 3.6m 场地约 **5-10 cm 漂移**
> - **导航到达精度**：`POS_TOL = 0.04m`，实测通常 ±3 cm
> - **抓取精度**：取决于 VLM 识别 + 标定精度，约 **1-3 cm**
> 
> 比赛任务点 40×40 cm，完全进入绰绰有余。

### Q7：你们的"锁航向"具体怎么锁？

> **答**：全程 P 控制器实时修正。每帧（50ms）读 tf 获取当前航向 → 算和目标航向的误差 → 算 `angular.z` 修正量 → 和 `linear.x/y` 一起发 `cmd_vel`。这样即使有外力干扰（地面不平等），航向也会被拉回去。同时，我们设置航向误差死区 0.02 rad（约 1°），避免频繁微调引起振荡。

### Q8：如果 amcl 在比赛中发散（位姿丢了）怎么办？

> **答**：我们有**纯里程计保底**脚本（`ten_point_odom_race.py`）。它只依赖 `odom → base_footprint`（EKF 一直运行，不依赖 amcl），不需要雷达和地图。虽然精度差一些，但可以拿到基本的到达分。这是我们的**容灾设计**。

### Q9：脚本超时时间为什么设 30 秒？

> **答**：比赛规则"30 秒不动即判负"。我们的 `STEP_TIMEOUT = 30` 意味着：如果某一步超过 30 秒还没完成，脚本会放弃那一步（`return False`），继续走下一点。这样避免死锁导致整场比赛被判负。**fail-fast 策略 → 宁可丢一点，不丢整场。**

### Q10：你们最怕什么故障？

> **答**：
> 1. **WiFi 断连** → VLM 没法用 → 抓不了物体（硬件问题，无冗余）
> 2. **amcl 定位跳跃** → 车以为自己在 A，实际在 B → 撞挡板（概率低但后果严重）
> 3. **串口被占** → 雷达或机械臂连不上 → 整场废了
> 
> 应对：第 1 点靠赛前测试 WiFi，第 2 点靠 fail-fast 机制，第 3 点靠开机 killall 清场。
