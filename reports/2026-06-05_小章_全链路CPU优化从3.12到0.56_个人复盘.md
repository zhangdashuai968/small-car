# 全链路 CPU 优化：从 load 3.12 到 0.56 的调试之旅

> 小章 · 2026-06-05

---

## 一、我怎么发现问题的

那天跑完六点巡逻 + 抓取测试后，我 SSH 到 Nano 上看了眼 `top`，吓了一跳：

```
load average: 3.12
```

Jetson Nano 只有 4 个核，3.12 意味着几乎满负载。更夸张的是：

```
gg.py (basic_xarm_grasp): CPU 98%
```

机械臂抓取节点占了整整一个核。它明明什么都没做，就在那等着 `/Pose` 消息。

我想起之前 Claude 说过全栈负载大概 1.3——实际跑起来翻了一倍不止。如果比赛时定位抖动、VLM 检测超时、机械臂动作滞后，根因可能就是 CPU 被吃光。

于是我决定逐层排查，找出所有 CPU 黑洞。

---

## 二、我是怎么一层层剥的

### 第一层：gg.py 98% → 3%

Claude 帮我读了 `gg.py`，没发现死循环。它依赖 `xarm_driver.py` 做串口通信。查 `xarm_driver.py`：

```python
def SerialRecvieCallback(self):
    while True:
        rx_len = self.__ser.inWaiting()
        if rx_len > 0:
            # 处理数据
```

就是这个 `while True`——没有数据的时候也在空转，`inWaiting()` 被每秒调用几万次。**修法**：没数据时 `time.sleep(0.02)`。

```
gg.py: 98% → 3%
load: 3.12 → 1.37
```

第一刀砍了 60%+ 的负载。

### 第二层：relay 桥接 11% → 0

之前为了让 gemini 摄像头和 image_zoomer 对接，我临时用了个 relay 节点做 topic 转发。Claude 指出这是多余的——直接改 launch 里的 remap 就行：

```xml
<remap from="/image_raw" to="/camera/rgb/image_raw"/>
```

relay 删掉，释放 11% CPU。

### 第三层：resize.py 50% → 21%

resize.py 在 30Hz 下对每帧图片做 ROI 裁剪 + INTER_CUBIC 放大。先加了帧跳过（每 2 帧处理 1 帧），效果立竿见影：

```
resize.py: 50% → 21%
```

但还是太高。30Hz 摄像头本身也有优化空间，降到 15Hz：

```
camera: 25% → 16%
load: 1.37 → ~1.3
```

### 第四层：能不能用 GPU？

Jetson Nano 有 Maxwell GPU（128 CUDA cores），但 `cv2.cuda.getCudaEnabledDeviceCount()` 返回 0。

查了一下：
- `apt install libopencv-python` → 4.1.1，无 CUDA
- `pip install opencv-python` → 4.6.0/4.11.0，manylinux wheel，无 CUDA
- `nvidia-opencv` meta-package → 只有 C++ 库，没有 Python 绑定
- FledglingTech/opencv-python-cuda-jetson → GitHub 上没有 release

**结论：没有现成的带 CUDA 的 OpenCV Python 包。必须自己编译。**

当时想过放弃——在 Nano 上编译 OpenCV 要 4-6 小时，中途 OOM、过热、断连都是风险。但想想 resize.py 从 50% 压到 21% 已经到 CPU 极限了，要想再降只能走 GPU。决定干。

## 三、本地编译 OpenCV CUDA

### 环境检查

```
CUDA 10.2 ✅
cuDNN 8.2.1 ✅
JetPack 4.6 / L4T R32.6.1 ✅
内存 4GB + Swap 4GB ✅
磁盘 22GB free ✅
```

### 编译踩坑

| 次数 | 错误 | 原因 | 怎么解决的 |
|------|------|------|-----------|
| 1 | 下载 wechat_qrcode 模型卡死 | GitHub raw 国内超时 | 禁掉 30+ 个不需要的 contrib 模块 |
| 2 | cmake 63% 报 OpenEXR 链接错误 | 内置 OpenEXR 链接顺序 bug | `-D WITH_OPENEXR=OFF` |
| 3 | cmake 100% 报 gapi perf_test 链接错误 | ADE 库链接失败 | `-D BUILD_opencv_gapi=OFF` |
| 4 | Python 绑定编译失败 | 重新 cmake 后生成头文件没刷新 | 删掉 `python_bindings_generator` 目录重建 |
| 5 | Python3 加载 4.1.1 系统版 | apt 安装的路径优先级更高 | `sudo rm /usr/lib/python3.6/dist-packages/cv2` |
| 6 | Python2 命令行 4.5.5，ROS 节点 4.11.0 | conda env 39 的 pip opencv 挡路 | 复制到正确路径 |

最终凌晨 1 点编译成功：

```
cv2.__version__: 4.5.5
cv2.cuda.getCudaEnabledDeviceCount(): 1
```

### resize.py 上 GPU 的坑

代码改完一跑就报错。前后炸了 4 次：

| 次数 | 错误 | 原因 | 怎么解决的 |
|------|------|------|-----------|
| 1 | `OpenCV(4.11.0) No CUDA support` | conda 39 激活后 `python` 指向 Python 3.9，加载了 pip 版 4.11.0 | 写死 shebang `/usr/bin/python2` |
| 2 | shebang 无效，还是 4.11.0 | ROS Melodic 不管 shebang，直接用 PATH 里的 `python` | 用 bash wrapper 脚本绕开 |
| 3 | `cv2.cuda.resize(src, dsize, dst)` → dst 下载后为空 | Python 绑定的 API 签名和 C++ 不一样 | 用返回值模式 `dst = cv2.cuda.resize(src, dsize)` |
| 4 | `TypeError: ... not 'NoneType'` | ROI numpy slice 是视图不是拷贝，GPU upload 要求连续内存 | 加 `.copy()` |

最后方案：

```
vl_locate.launch
├── resize_gpu.sh  ← bash wrapper: exec /usr/bin/python2 resize_core.py
├── resize_core.py ← GPU cv2.cuda.resize(INTER_CUBIC)
└── server.py      ← conda Python 3.9 + OpenAI (互不干扰)
```

## 五、反思

### 做对了的

1. **自上而下排查**——先看 `top` 找最大消耗，逐个击破，不急着重写代码
2. **保留备份**——每次改都 `.bak`，踩坑能回退
3. **API 测试先行**——`cv2.cuda.resize` 用 Python 单行脚本验证后再改

### 踩坑教训

1. **ROS Melodic 不看 shebang**——它会用 PATH 里的 `python`。以后任何需要特定 Python 版本的节点，用 bash wrapper
2. **conda 和 ROS 的 PATH 冲突**——conda 激活后会劫持 `python`/`python3`，和 ROS 的 Python 2.7 混用必出问题
3. **Nano 编译 OpenCV 不容易**——虽然成功了，但中途踩了 6 个坑。`cmake_cuda.py` 脚本已经固化，下次重建环境能直接用

### 如果重做

我会先把 `xarm_driver.py` 的 `time.sleep(0.02)` 和 relay 桥接修复作为独立补丁提交——这两个改动小而收益大（98%→3% + 11%→0），不需要等 OpenCV 编译完。GPU 优化单独走一个分支，测试稳定后再合。
